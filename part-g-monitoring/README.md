# Part G - Monitoring

## About the question: 

    HRM Labs wants to monitor its production application.
        • Server: CPU, RAM, disk, network, load
        • Application: response time, error rate, HTTP status codes, request volume, logs
        • Infrastructure: container status, database availability, database connections, uptime
    31. What would trigger an alert?
    32. Who should receive the alert?
    33. What is the difference between monitoring and logging?
    34. If HRM Labs has 20 servers, how would you avoid manually checking each server every day?

## Answers

### 31. What would trigger an alert?

I would prioritize alerts for metrics that can directly affect system availability and stability, such as server availability, database availability, database connection exhaustion, disk usage, CPU usage, and memory usage.

For example, I would trigger an alert if a server becomes unreachable, the database becomes unavailable, database connections are exhausted, disk usage becomes critically high, or CPU and memory usage remain high for a certain period.

I would also monitor application-level metrics such as high error rates and slow response times because infrastructure resources may appear healthy while the application itself is still experiencing problems.

### 32. Who should receive the alert?

I would route alerts to the team responsible for the affected component.

Infrastructure-related alerts, such as CPU, memory, disk, network, or server availability, should be sent to the DevOps or System Administration team.
Database-related alerts, such as database availability or connection issues, should be sent to the DBA or database team, and potentially the DevOps team.
Application-related alerts, such as high HTTP 5xx error rates, slow response times, or application errors, should be sent to the development team or the on-call application engineer.
Critical production incidents should also be escalated to the relevant Team Lead or incident response team.

### 33. What is the difference between monitoring and logging?

Monitoring and logging are both important for maintaining system reliability, but they serve different purposes.

Monitoring focuses on continuously observing the health and performance of the system, using metrics such as CPU usage, memory usage, response time, error rate, and availability. It can detect abnormal conditions and trigger alerts.

Logging records detailed events and activities generated by the system, such as application errors, requests, and database failures. Logs are mainly used to investigate problems and identify their root causes.

In simple terms, monitoring tells us that something is wrong, while logging helps us understand what happened and why.

### 34. If HRM Labs has 20 servers, how would you avoid manually checking each server every day?

If HRM Labs has 20 servers, I would avoid manually checking each server every day. First, I would define the monitoring requirements with the relevant stakeholders and development/operations teams, such as acceptable response time, error rate, resource thresholds, database availability, and uptime requirements.

Then I would implement a centralized monitoring and alerting system for all servers. The system would collect metrics and application information from the servers and provide a centralized dashboard. I would configure alerts for important conditions and send notifications to the responsible team through channels such as Telegram, email, or Slack.

When an alert is triggered, I would investigate the affected server or application, check the monitoring data and logs, identify the root cause, and take the appropriate corrective action.
